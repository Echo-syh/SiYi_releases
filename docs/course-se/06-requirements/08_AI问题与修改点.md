# AI 输出问题与我的修改点

> 这份记录只写「AI 说了什么、哪里不对、我怎么改、依据是什么」。不把 AI 的初稿包装成最终稿。

## 1. 策略 A（访谈式）暴露的问题

| # | AI 的输出 / 行为 | 问题类型 | 我的修改 | 依据 |
| --- | --- | --- | --- | --- |
| A-1 | 需求里直接写 Electron、SQLite、Ctrl+K、`%APPDATA%\siyi` | 方案混入 / 过度约束 | 删除技术选型，只保留「Windows 桌面」「全局快捷键可唤起」「数据在本机可定位」这类能力描述 | 需求应说明 what/why，不规定 how；技术选型属于设计约束，且会随实现变化 |
| A-2 | FR-A-05 把「按需读页 + 全文检索 + 页码依据」塞进一条 | 复合需求 | 拆成「基于正文回答」「按需读取/检索」「引用可核对」三条，分别验收 | 一条需求只能有一个可判定的通过条件 |
| A-3 | 「中文两个字就能搜到」 | 不可度量 | 改为「≥2 字中文查询可命中正文；2 字走 LIKE、≥3 字走 FTS trigram；用固定测试集验收」 | 原文没有定义「搜到」的判据；实现机制也决定了短词与长词走不同路径 |
| A-4 | 「首字 2 秒内」 | 测量条件缺失 | 改为「服务端首字节到达后 2 秒内开始渲染；网络与服务商排队时间单列」 | 端到端首字受网络、限流、模型负载影响，不能都算在软件头上 |
| A-5 | 「本地优先」与「把论文发给 LLM」并列，未划界 | 矛盾未解 | 增补边界声明：数据静态存储在本机；离开本机的只有用户主动触发的 LLM 请求、CrossRef DOI 查询、本机翻译服务；发送范围可见 | 原始构想本身包含这对矛盾，必须显式解决，不能靠措辞糊过去 |
| A-6 | 未覆盖 429、上下文超限、静默截断、流式中断 | 缺失场景 | 补「错误分类可见」「部分阅读透明」「不得把未读说成不存在」三条 | 用户 Agent 的叙述里这些都是信任崩塌点；访谈时没问到 |
| A-7 | 访谈由同一模型分饰访谈者与开发者 | 方法缺陷 / 自我确认偏差 | 不假装它是真实分歧；把这一点写进对比分析，并用策略 C 的独立 Agent 交叉验证 | 同一模型扮演双方时，提问会不自觉地避开自己答不上来的地方 |
| A-8 | 「导师偶尔看笔记」只推出「导出 Markdown」 | 需求收窄过早 | 保留导出，但把「分享/协作」明确列为范围外，并写理由 | 访谈中的一句旁支不等于产品范围；要区分「能导出」与「能协作」 |
| A-9 | 性能指标写成单点数字，没有参考机与样本 | 不可复现 | 补参考机、冷/热启动、样本量、测量方法 | 没有测量条件的性能指标只是愿望 |
| A-10 | 把「像 Zotero 那样」直接当成「支持 Zotero 导入」 | 歧义未澄清 | 拆成「Zotero 式组织方式」与「一次性迁移」两件事；后者加数据质量预检 | 实际项目里 Zotero 库可能不是规范文献库，盲目导入只会得到同样脏的库 |

## 2. 策略 C（多 Agent）暴露的问题

| # | AI 的输出 / 行为 | 问题类型 | 我的修改 | 依据 |
| --- | --- | --- | --- | --- |
| C-1 | FR-03「并排显示 + 分隔条可拖动」 | UI 方案混入需求 | 改为「阅读与问答可在同一窗口协作，具体布局不作规定」 | 原始构想只说「旁边就能问」，没有规定分隔条 |
| C-2 | FR-17「逐段对齐的原文/译文对照」 | 依赖外部工具能力，未验证 | 改为「提供原文/译文对照；对齐粒度以翻译服务实际输出为准，验收时抽样」 | 翻译由外部工具完成，需求不能替它承诺逐段对齐 |
| C-3 | FR-18「译文按页缓存」 | 实现细节 | 改为「译文副本随论文保存；重复查看不重复翻译、不重复计费」 | 缓存粒度是实现选择，不是用户可感知的需求 |
| C-4 | NFR-01「4 核/16GB、50MB/500 页 3 秒、2000 篇 1 秒」 | 拍脑袋数字 | 改为「参考机 + 实测记录 + 分级目标」，发布前用固定样本测 | 没有测量环境和样本的数字不可验收 |
| C-5 | NFR-05「5 名目标用户中 4 人无需文档完成」 | 课程项目不可行 / 过度设计 | 改为「开发者 + 2 名同学走查核心流程，记录卡点与耗时」 | 单人一学期的项目没有 5 名目标用户的招募与实验条件 |
| C-6 | NFR-04「100 次启动退出后条目数不变」 | 过度具体、场景错位 | 改为「重复启动/退出、异常退出后不产生重复条目或数据损坏」 | 启动退出次数不是关键变量，数据一致性才是 |
| C-7 | NFR-09「30 分钟抓包」 | 验收成本高 | 改为「外联目标白名单 + 代码审查 + 一次抓包抽查」 | 需求要可验收，但不必把每次验收都做成网络取证 |
| C-8 | 范围外直接砍掉 PDF 标注、多端同步、移动端、OCR | 与用户诉求冲突，未说明取舍 | 不直接砍：标注/移动端列为 v2，多端同步列为范围外并说明「本地优先优先于同步」；OCR 只做「明确告知不可读」，不默认上云 | 用户 Agent 明确说「有更好」和「会弃用」，需求不能装作没听见 |
| C-9 | 缺 Zotero 迁移、重复导入、原文件丢失重定位 | 缺失场景 | 补三条 FR，并把 Zotero 迁移降级为「数据合格时的一次性导入」 | 这三件事在真实使用中高频，且直接决定文库是否可用 |
| C-10 | 缺「点击页码跳到原文」 | 缺失场景 | 补「引用需可定位；若无法定位必须明示」 | 用户三条最强诉求的第一条就是「点一下能跳」 |
| C-11 | 用户 Agent 自述里的 AAV 序列、临床数据、三台设备 | 角色扮演细节，不是用户事实 | 不作为需求依据；只提取通用诉求（隐私、费用、换机、协作） | 子 Agent 的用户画像不等于真实用户；不能把虚构细节写进需求 |
| C-12 | 「翻译不能把否定翻反」 | 无法由软件单方面保证 | 改为「对否定、数值、术语三类做抽样验收；翻译结果标明由外部服务生成」 | 翻译质量取决于外部模型与服务，软件只能做抽检与提示 |
| C-13 | 「手机上也能看」「导出 BibTeX」 | 超出原始构想 | 列为 v2 / 范围外，不进入 v1 验收 | 原始构想只提 Windows 桌面；范围要收敛 |
| C-14 | 评审者只审文档，不审现实 | 方法局限 | 增加「拿现有实现做一致性抽查」这一步 | 文档内部自洽不等于需求可实现；必须对证据 |

## 3. 评审者发现的问题

评审者对分析师初版的结论是「不能进入下一阶段，只能进入修订后复审」。以下按严重度列出它抓出的主要问题，以及最终版的处理。

| # | 评审者发现 | 类型 | 严重度 | 最终版处理 |
| --- | --- | --- | --- | --- |
| R-1 | 把「不传到别人服务器」改写成假设 A4「用户接受发给外部模型」，同时把本地模型列为范围外，等于取消退路 | 矛盾 | 高 | 新增 1.4 边界裁决：显式告知、默认最小发送、可关闭 AI、本地模型列 v2；不再用假设糊过去 |
| R-2 | FR-11「无依据时明示未找到」与 FR-15「截断标部分内容」叠加，会复现「悄悄截断后说文中未提及」 | 一致性 | 高 | FR-07 改为三态：全文覆盖/部分覆盖/未找到；部分覆盖禁止输出「没有提到」 |
| R-3 | 页码若由模型生成必然编造，而「编页码」是弃用条件；需求没区分模型自述与系统校验 | 正确性 | 高 | FR-06 规定引用只能来自抽取层页-段映射/工具结果；模型自报页码不得直接作为可跳转引用 |
| R-4 | 用户明确「中文搜不到英文术语」，需求无跨语言要求 | 缺失 | 高 | FR-17 增加 脱靶/off-target、半衰期/half-life、野生型/wild-type 三组验收；不支持须明示 |
| R-5 | 用户要「开六个 PDF 找原话、标清哪篇哪节」，需求只有单篇上下文 | 缺失 | 高 | 列为 v1.1；v1 明确不承诺跨篇汇总，提供逐篇提问+文库检索作为替代 |
| R-6 | 双栏、页眉页脚、公式、表格列错位、± 误判都在用户异常清单里，需求只有「支持带文本层 PDF」 | 缺失 | 高 | NFR-15 增加固定抽取样本集（6 类各≥2 篇）与人工核对 |
| R-7 | 「翻译把否定翻反」是弃用级，需求无译文质量门槛 | 缺失 | 高 | FR-18 增加否定/数值/专名抽样验收；明确译文由外部生成，软件不保证正确，可标记问题 |
| R-8 | FR-15「按片段选取」是检索实现，且与「真读全文」冲突 | 过度设计 | 高 | 改为结果约束（FR-07 三态），选取策略留给设计 |
| R-9 | 3 秒、1 秒、5 秒、300ms、5 人 4 人、125%–200% 均无实测来源；2000 篇与 5000 篇口径不一 | 无依据 | 高 | NFR-01 改为「初始目标、发布前实测回填」；可用性改为 2 名同学走查；库规模统一 |
| R-10 | 元数据来源未定义，而用户痛点正是「经常抓错」 | 歧义 | 中 | FR-10 明确 DOI→CrossRef、失败可手填；补「抓取失败/低置信不得写入错误值」 |

| R-12 | 「卸载无残留」与「数据根目录可指定/整库导出」冲突 | 矛盾 | 中 | FR-24 区分程序与数据：卸载默认保留；彻底删除只清理配置的根目录 |

| R-14 | 流式停在半句、429、不报错不保留 | 缺失 | 中 | FR-23 增加 429 退避、半截保留并标记「未完成」、可续写 |

## 4. 最终取舍原则

1. **需求说 what/why，不说 how**：技术栈、控件、缓存粒度、目录结构一律不进需求。
2. **每条可验收**：不能验收的，要么改成可观测的判据，要么降级为「开放问题」。
3. **不把实现现状写成需求**：实现是证据，不是目标；「现在有」不等于「必须有」。
4. **不把愿望写成承诺**：外部服务（LLM、翻译）的能力边界要写清，软件不替它们打包票。
5. **冲突显式解决**：本地优先 vs 云端模型，用「静态数据本地 + 传输范围可见」划界，而不是含糊其辞。
6. **版本分层**：v1 必须、v1.1 增强、v2/范围外；砍掉的东西要写理由，不静默消失。
