# 两套策略对比分析

## 0. 对比口径

| 版本 | 来源 | 说明 |
| --- | --- | --- |
| A | `02_策略A_访谈记录.md` + `03_策略A_需求与用例.md` | 访谈式，3 轮 22 问，访谈者与开发者由同一模型分饰 |
| C 初版 | `04_策略C_多Agent记录.md` 的分析师输出 | 用户/分析师两个独立 Agent 只拿原始构想，产出 25 FR / 15 NFR / 9 UC |

> 说明：C 修订版是在评审者打回后产生的，不能当作「C 一次就做对了」；恰恰相反，C 初版被判了「不能进入下一阶段」。两套输出的差异，一部分来自角色约束，一部分来自输入信息不同，见第 5 节。

## 2. 需求完整性

### 2.1 A 强在系统边界，弱在用户信任边界

A 的访谈把「软件与外部系统的职责」问得比较清楚：

- 不做文献下载/爬取、不做翻译排版重建、翻译调外部服务、AGPL 不打包；
- 重复导入、附件丢失、扫描件、加密件、强杀恢复、翻译服务未启动，这些「系统会遇到的异常」都有对应需求；
- 性能、可靠性、安全、兼容性、合规都有可验收的条目。

但 A 漏掉的，恰好是用户最在意的信任问题：

- **页码引用是否可信**：A 只说「回答要能指回页码」，没说页码从哪来、模型能不能自报；
- **部分阅读是否透明**：A 说了「部分内容要标注」，但没有定义「部分覆盖时不许说未找到」；
- **中英术语检索**：A 只写「中文两个字能搜到」，没覆盖「中文搜英文论文」；
- **批注随版本丢失**：A 完全没提；
- **多设备/换电脑**：A 只想到「笔记导出」，没想到整库迁移；
- **多篇论文联合找原话**：A 没有这个场景。

### 2.2 C 强在用户痛点，弱在可开发边界

C 的用户 Agent 贡献了 A 没有的东西：

- 编页码/编引文是「一次就失去信任」的弃用条件；
- 流式输出停在半句、不报错不保留；
- 429、上下文超限、悄悄截断后说「文中未提及」；
- 中文搜不到英文术语（脱靶/off-target、半衰期/half-life、野生型/wild-type）；
- 批注做在 arXiv v1 上、组会念了后来改掉的数字；
- 库目录移动后两百多条「找不到文件」；
- 「我当时为什么这么判断」这句话最值钱。

但 C 的分析师初版把这些痛点大多留在了「风险」或「范围外」：

- 双栏硬换行、页眉页脚、表格列错位、± 被当小数点 → 只写「支持带文本层 PDF」；
- 翻译否定翻反 → 没有任何译文质量门槛；
- 批注丢失 → 直接列为范围外；
- 多篇联合提问 → 没有；
- Zotero 迁移 → 只写「假设一次性导入」，没有对应 FR。

### 2.3 结论

- **A 的完整性是「系统能跑」的完整性**：异常、约束、职责划分比较全。
- **C 的完整性是「用户敢用」的完整性**：信任阈值、失败模式、历史找回比较全。
- 两者都不完整，但缺的不是同一块。最终版把两块拼起来，才有 24 条 FR / 16 条 NFR / 14 个用例、26 项边界覆盖 24 项的结果。

## 3. 是否产生幻觉

先定义口径：**「幻觉」指在原始构想和用户证据里找不到依据，却被写成确定需求的内容**；合理补充但标注了 `[假设]` 的，不算幻觉，算假设。

### 3.1 A 的幻觉：0 个新功能，但有 3 处方案混入

A 没有编造产品功能，但把实现方案写进了需求：

| 位置 | 原话 | 问题 |
| --- | --- | --- |
| FR-A-11 / NFR-A-07 | Electron、SQLite、`%APPDATA%\siyi` | 技术选型，不是需求 |
| FR-A-09 | Ctrl+K | 具体快捷键，不是需求 |
| NFR-A-01 / NFR-A-09 | 3 秒、2 秒、500 毫秒 | 目标值没有测量条件，接近「拍脑袋」 |

A 的「访谈者」和「开发者」是同一个模型，所以它不会提出自己答不上来的问题；这是方法上的自我确认偏差，不是幻觉，但会让需求看起来比实际更确定。

### 3.2 C 初版的幻觉：8 处无依据的确定需求

| 位置 | 内容 | 为什么算幻觉 |
| --- | --- | --- |
| FR-02 | 显示 PDF 目录并可点击跳转 | 原始构想没提；标了 `[假设]`，但列在「功能性需求」里像确定项 |
| FR-03 | 并排显示 + 分隔条可拖动 | 原始构想只说「旁边就能问」，没规定布局 |
| FR-05 | 重开论文恢复上次阅读位置 | 合理，但没标假设 |
| FR-07 | 批量修改标签 | 用户没提，分析师加的 |
| FR-17 | 逐段对齐的原文/译文对照 | 依赖外部翻译工具能力，未验证 |
| FR-18 | 译文按页缓存 | 实现细节，不是用户可感知的需求 |
| NFR-05 | 5 名目标用户中 4 人无需文档 | 没有招募来源；单机单用户假设下测试对象不存在 |
| NFR-06 | 不超过 2 次点击、自定义快捷键 | 用户从未提；「主要按钮带文字」也不可判定 |

此外还有 4 处「看起来可验收、其实没有来源」的数字：3 秒、1 秒、5 秒、300ms；以及 2000 篇 vs 5000 篇的口径矛盾。

### 3.3 C 修订版：0 处未标注的幻觉

评审者把上述 8 处逐一处理：删除（分隔条、逐段对齐、按页缓存、5 人测试、2 次点击）、改写（按片段选取 → 三态结果约束）、标假设（目录、恢复位置）、补来源（性能改为「初始目标、实测回填」）。

这说明：**多 Agent 本身不消除幻觉，评审环节才消除幻觉**。如果没有第三个 Agent 拿着原始构想逐条对照，C 初版的幻觉会原样进入需求文档。

## 5. 效率

| 维度 | A | C |
| --- | --- | --- |
| 交互轮次 | 3 轮 22 问 | 2 个 Agent 并行 + 1 个评审 + 1 轮修订 |
| 墙钟时间 | 一轮生成（分钟级） | 约 6–7 分钟（并行后仍比 A 慢） |
| Token 成本 | 约 1 万 | 约 13 万 |
| 人的参与 | 需要有人回答 22 个问题 | 需要设计 3 个角色提示词、整合评审意见 |
| 可并行 | 否（访谈是串行的） | 是（用户/分析师可并行） |
| 返工成本 | 低（一条线走到底） | 高（初版被打回，需修订） |

**结论**：A 更便宜、更快，适合「开发者自己就在场」的场景；C 更贵、更慢，但它买到了「独立视角 + 对抗性评审」。如果只是想要一份能开发的功能清单，A 够了；如果要想清楚「用户为什么不敢用」，C 的评审环节值这个钱。

## 6. 存在的缺陷

### 6.1 A 的缺陷

1. **自我确认偏差**：访谈者和开发者是同一个模型，问题会绕开自己答不上来的地方；22 问看起来很全，但没有真正的分歧。
2. **方案混入**：技术栈、快捷键、目录写进需求，导致需求不可移植。
3. **复合需求**：一条 FR 里塞多个可判定条件，验收时容易扯皮。
4. **用户信任边界缺失**：页码来源、部分覆盖、中英检索、批注丢失、多设备都没问到。
5. **不可度量的表述**：「中文两个字就能搜到」「快速」「友好」这类词没有验收口径。

### 6.2 C 的缺陷

1. **初版是功能清单，不是验收基线**：25 条 FR 看起来完整，但把用户的「不外传」改写成了「用户接受外发」。
2. **无依据的数字和 UI 方案**：5 人可用性测试、2000 篇/1 秒、并排分隔条、逐段对齐、按页缓存。
3. **评审者只能审文档**：它不知道 500 页 PDF 首屏 2 秒在真实机器上是否成立，也不知道 Zotero 导入为什么被撤掉；这些必须靠实现核对。
4. **角色提示词决定质量**：如果评审者只被要求「看看有没有问题」，它会顺着文档逻辑挑毛病，挑不出「需求已经改写掉用户诉求」。
5. **成本高**：13 万 token、3 个 Agent，换来的是一份需要再修订的初稿。

### 6.3 两套共有的缺陷

1. **没有真实用户**：所有「用户」都是模型扮演的；真正的用户访谈、可用性测试都没有做。
2. **没有真实取舍人**：范围砍不砍、隐私边界怎么划，最终要由开发者/课程要求拍板，模型只能给选项。
3. **需求与实现的核对不充分**：A 完全没有核对实现；C 只核对了文档，直到最后一步才拿源码做抽查。
4. **无法验证「需求是否值得做」**：两套都在回答「怎么做」，没有回答「值不值得做」；商业/社会可行性只能给定性判断。

## 7. 差异是怎么造成的

1. **输入信息不同**：A 的「开发者」知道产品边界，所以系统异常问得细；C 的用户/分析师只有一段原始构想，所以用户痛点靠角色扮演补，系统边界靠常识补。
2. **角色是否分离**：A 是同一模型分饰两角，提问和回答共享同一套盲区；C 的三个 Agent 独立运行，评审者拿不到分析师的「自我解释」，只能对着原始构想挑错。
3. **有没有评审环节**：C 的初版和修订版差距，几乎全部来自评审者。评审者抓到的不是「条目多少」，而是「隐私被降级」「页码由模型自报」「验收数字无来源」这类结构性问题。
4. **提示词的导向**：分析师被要求「不写技术选型、标假设」，所以 C 初版的方案混入比 A 少；但也被要求「完整」，于是发明了 5 人测试、2000 篇/1 秒这类「看起来完整」的数字。
5. **输出格式**：A 的问答格式天然带溯源（每条 FR 能指回 Q/A）；C 的结构化格式鼓励覆盖，却容易把「合理猜测」写成「确定需求」。

## 8. 结论：怎么选

- **如果开发者自己就在场、目标是尽快得到一份能开发的基线**：选 A。它便宜、快、可溯源，系统边界清楚；但要补三件事——把方案从需求里剔出去、把复合需求拆开、找一个人（或一个 Agent）拿着原始构想做对抗评审。
- **如果目标是把用户信任边界和异常场景挖干净**：选 C。它的用户 Agent 和评审者能产出 A 想不到的失败模式；但必须接受「初版会被打回」，并且评审者的提示词要足够狠。
- **这次最终采用的是混合路线**：A 的骨架（问题—范围—职责—FR/NFR/UC—验证）+ C 的用户信任边界（页码来源、三态、静默截断、中英检索、批注、多设备）+ 评审者的纪律（删数字、删 UI 方案、标假设）+ 实现核对（拿源码验证需求是否说得通）。

一句话：**A 让需求「能开发」，C 让需求「敢使用」，评审让需求「不骗人」。三者缺一不可。**

## 9. 这次对比本身的局限

1. 五个角色全是 AI，没有真实用户、真实导师、真实同学参与；「用户 Agent」的科研日常是角色扮演，不是访谈记录。
2. C 修订版是在评审后产生的，拿它和 A 的初版比，对 A 不公平；所以第 1 节同时列了 C 初版和修订版。
3. 开发者（我）已经知道产品做成了什么样，访谈时不可能完全「回到开发前」；A 的很多回答带有事后合理化。
4. 没有做真实可用性测试，NFR 里的性能/易用性数字只能是目标，不能当结论。
5. 对比的是「两套交互策略」，不是「两种模型」；同一模型在三种角色下的表现，不能推广成「多 Agent 一定优于访谈」。
