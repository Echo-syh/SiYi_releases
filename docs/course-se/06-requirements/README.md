# 思懿 · 需求获取记录（软件工程第六讲作业）

上海交通大学《软件工程》第六讲作业「需求获取」。选题是思懿——本仓库发布的这个应用。做法是把需求阶段倒带回开发前重做一遍：从一段原始构想出发，用两种交互策略让大模型做需求启发，再拿已有的实现当标准答案做验证。

## 结论

两种策略的产出不一样：

- **策略 A（访谈）**系统边界清楚，异常问得细，每条需求能指回具体哪一问。但它不会问自己答不上来的问题——访谈者和开发者是同一个模型，22 个问题没有一次真正的分歧。
- **策略 C（多 Agent）**的用户 Agent 写出了访谈完全没覆盖的信任问题：编页码、编引文、嘴上说本地实际外发、翻译把否定翻反。评审者按八条标准逐条对照，把分析师初版打回「不能进入下一阶段」。

最终版不是两套的拼接，而是五次裁决：把隐私矛盾写死、把回答改成三态、把页码来源钉死、补中英互搜、给 PDF 抽取质量建样本集。另有一项取舍——Zotero 导入从 v1 降到 v1.1，因为原始构想里那句「像 Zotero 那样」在开发时被证明有歧义。

## 说明

- 所有角色都由 Claude 扮演。这不是多人评审，是同一模型在不同角色约束下的自我对抗；它的价值和局限写在主文最后一节。
- 与现有实现的对照只用于**验证需求是否说得通**，不把实现现状当成需求。实现是证据，不是目标。
- 记录来自真实对话与真实子 Agent 输出，逐字或摘要保存，未事后润色。
